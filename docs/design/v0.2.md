# ConfIt v0.2 design

Design spec behind v0.2.

Status: Implemented (sealed 2026-09-12)

## Motivation

Plan covers desired and previous. This version adds the third source,
the actual files on disk, because I keep testing features on my
dotfiles and wiping things out. Fixing a nim install error once took
my zsh config with it, history tricks, always-store-history, the warp
fix for zoxide, utility functions like up. Never one catastrophe I
cannot work around, just a lot of small pains and rework every time.

A diff between generated output and disk state shows modifications at
a glance, so nothing disappears silently again.

File resources matter because real tools ship structured configs that
change per machine. Starship, vscode, and in general every tool
someone tweaks. My laptop is slower than my pc so it wants a higher
timeout, my desktop screen is bigger than my laptop so vscode or
ghostty want a different font size there. Static tables cannot express
that, so tools parametrize and merge.

Sharp layer homes matter. Each version piles more on top, so the
moves happen now while they stay cheap.

## Objective

Make `plan` diff desired vs previous vs actual, proven by two
fixtures: `examples/1-structured_resource`, a starship-like tool,
parametrized from Lua, with a `starship.toml` config resource built
through the paths lib; plus `examples/2-templated_resource`, the same
tool reading its config as a minijinja template with profile variables
instead of decoding to a Lua table and re-encoding.

## Goals

- Filesystem-aware plan: read each artifact path, hash the bytes.
- Manual-edit warnings: disk differs from what the record says, user gets
  told. Absent paths read as absence. Failing reads warn and continue.
- Diff generation: per-artifact diff between generated and current,
  showing modifications at a glance. Structured kinds diff at key-value
  level, scripts and raw bytes diff as unified hunks.
- File resources: static and templated files to copy, attached to tools
  like any other contribution.
- Resources namespace: `confit.resources.load_toml/load_json/load_yaml`
  (root-relative reads to Lua tables), `confit.resources.merge` (deep,
  last-wins), `confit.artifact.*` constructors, `tool:append_artifact`.
- `confit.path` lib: `home`, `config`, `data`, `confroot` helpers.
- Layered architecture: every module moves to the layer it belongs to,
  tracked in `docs/architecture.md`. Shared data centralizes in
  `model`: state entities in one group, transfer shapes in another.
- Diff/presentation split: services shape data, presentation owns
  every string the user sees, with color.
- One hashing home: snapshots, digests, and plan ids share one root
  utility instead of scattered copies.
- Init source entries: `tool:init({ source = "path" })` renders
  `source path`, so eval, exec, and source are all covered. The
  source takes a plain path string for now. Pointing it at an
  artifact reference waits until that shape exists.

## Plan

### Filesystem-Aware Plan

Read each artifact path, SHA-256 the bytes. `~` and XDG folders
resolve through the `directories` crate. Absent paths read as absence.
Failing reads warn naming path and reason, read as absent, exit stays 0.

Best effort strategy. Not read counts as different with a warning. I
do my best effort but assume the worst, plan never stops for that, and
the user decides if files match, differ, or need permission fixes. Advice
is all we can do, and it is not an error either way.

Invariant: warnings ride along with a successful run. Exit stays 0 while
warnings exist. Errors print through the crate error type and exit 1.

### Manual-Edit Warnings

Every row below exists so no line dies silently, same wipe story as
the diff.

- Empty record plus absent path reads as create. Nothing exists
  anywhere, the file comes fresh.
- Empty record plus present path reads as create with an
  overwrite-untracked warning, the file gets destroyed otherwise.
  This is the row the whole project exists for.
- Record plus matching desired plus differing disk reads as update
  with a manual-modification warning. Someone touched the file by
  hand since last time.
- Record plus changed desired reads as update. The config moved, the
  file follows.
- Record plus absent desired reads as delete. The config dropped it,
  the record keeps the memory.
- Failing reads add an unreadable warning and read as absent.
  Best effort, the user decides if files match, differ, or need
  permission fixes.

Warnings travel back with the outcome; `main` prints them to stderr.
In real use they arrive in that order, untracked first, then manual
modifications, then unreadable paths.

### Diff Generation

The main reason I build this, aside from old dotfiles scripts being
impossible to maintain, is that I am exhausted from wiping out my
config while working on those scripts. Worst case I remove lines from
software that installed and auto configured itself, and I dont know
how to reconfigure it. Or I uninstall tools. Or I delete manual
configs with no warning at all. I want the plan to give me the chance
to say "Oh gosh, I forgot this" and add it to my config instead of
losing it.

So every plan shows two things before touching anything. First what
changed outside the config since last time, because those lines get
overwritten. Then what the config wants to change, with the winner on
each entry. The preview-before-apply loop plus the drift display
borrow from Terraform, which solved this exact fear first.

Structured kinds diff at key level, scripts and raw bytes diff as
unified hunks. The hunks come from a borrowed differ wearing our
headers. The example below shows the moment, a forgotten timeout
about to be overwritten next to the change asking for it.

Invariant: hunk headers read `--- on disk` and `+++ desired`, followed
by one `@@` range per hunk. Body lines carry `+`, `-`, or space marks.

```sh
Note: Objects have changed outside of ConfIt

ConfIt detected the following changes made outside of ConfIt since the last recorded state:

  # ~/.config/starship.toml has changed
  ~ artifact "toml" "~/.config/starship.toml" {
      ~ command_timeout = 500 -> 10000 (will be overwritten)
        # (all other unchanged attributes hidden)
    }

~/.config/starship.toml: toml ← starship
  + palette = "catppuccin" (starship)
Plan: 1 to add, 0 to change, 0 to destroy.
```

### File Resources

Tools are a conceptual grouping of mergeable artifacts, ConfigSets in
some sense. Not every ConfigSet is a tool, fonts are not tools and
configs for tools we do not install are not tools either. The name may
change in the future, it works for now.

Static plus templated files attach to tools like any other
contribution and copy over as real dotfiles: rc text with markers and
escaped argv, toml/json/yaml serialization, file bytes, template
rendering with `src` reads under `--root`.

> Note: the `tool` name covers ConfigSets for now and may change in a
> future version.
>
> Plan hooks are gone on purpose. The old implementation was
> half-broken and useless before `apply` replaces files, so a formal
> design waits until that part works. Plan still has pending work of
> its own, alias guards and install checks among it, and hooks are not
> needed in the near horizon.

### Resources Namespace

The namespace was born to grant two things.

1. Availability of resources in configuration, so users do not need
to create all of them in Lua. Structured formats are better for that.
2. Modifying those structured resources with Lua semantics, accessing
them like normal tables, which gives profiles their flexibility.

Trying to read outside the confroot marked in the CLI (`--root`)
is either a mistake or someone exploiting the tool to reach into the
filesystem, so I make it a hard plan error either way. `merge` recurses tables,
everything else (arrays included) last-wins wholesale.
An option table tweaks it for the two real cases: starship replaces
the prompt array with the profile's own, so `shallow = true` merges top-level
keys alone with nested tables replaced wholesale.
Warp appends its plugin to the opencode config instead of removing user plugins,
so `list_append = true` concatenates arrays, keeping duplicates.
An unknown option key is either a typo or a guess at an option that
does not exist, and silently ignoring it would run a merge nobody
asked for, so that fails as a plan error too.

```lua
return function(user_config)
  local resource = confit.resources.load_toml("resources/starship.toml")
  local config = confit.resources.merge(resource, user_config)
  local artifact = confit.artifact.toml(
    confit.path.config("starship.toml"),
    config
  )
  starship:append_artifact(artifact)
  return starship
end
```

> Note: the split across profile, tool file, and resources folder is
> just organization I propose, all of it could live in the same profile
> file. Tool files returning a parametrizing function is the same kind
> of choice, it just emerged thinking about per-profile configurations.
> Lua can return whatever, only the resulting tool set matters.

### `confit.path` lib

Pure functions returning plain strings for joins:

- `home("src")` goes to `$HOME/src`.
- `config("starship.toml")` goes to the OS config folder
  (`$XDG_CONFIG_HOME` or `~/.config`). Managed files land here.
- `data("fonts/JetBrainsMono")` goes to the OS data folder
  (`$XDG_DATA_HOME` or `~/.local/share`). Local installs like fonts
  land here.
- `confroot("templates/app.conf.j2")` goes to the confit project tree
  (`--root` flag): template sources, link targets, shipped defaults.
  `confroot` serves symlinks to shipped resources.

All OS folders resolve through the `directories` crate, so authors
never hand-roll XDG paths. `$XDG_CONFIG_HOME` is not always `~` and
users writing `~` get different results than `home()`, so a function
checked by the LSP beats a var everyone misremembers. `config`
receives managed files, `confroot` serves project sources and stays
for symlinks to shipped resources. `data` serves local installs like
fonts.

### Layered Architecture

Taking inspiration from layered architectures used in web apps, I want
a clearer separation of concerns, so the app stays easy to maintain
and debug. Right now logic, presentation, data transformation, and IO
sit highly coupled in small islands built per feature. When the plan
output looks wrong, nothing tells me whether presenting the data
failed, generating the diff failed, or collecting the artifacts
failed.

#### DTO and State Centralization

The first step is centralizing the entities modeling all behavior in
the app, plus the entities layers use to talk to each other, even
across services in one layer but different domains. I am a DevOps
engineer without deep software architecture knowledge, but this shape
works in my other personal projects.

For this app I split it in two groups. State entities cover everything
generated from Lua and applied. Transfer shapes cover everything layers
exchange, owned by no single domain, which kept forcing layers to reach
across each other until the graph stopped being a DAG.

#### Use the Repository pattern

Borrowing from web, again, I want to re-use the Repository pattern
where external effects are abstracted away from an actual
implementation into an interface (Rust trait in this case) to be able
to easily mock up in tests (I dont want my dotfiles wiped out again
in tests).

#### Lua Split

On Lua side, is complicated, so I split it in two layers.

1. The Evaluator. That is basically another repository but since 1. it
has its own domain and 2. it is read only, I do not give it the same
trait treatment I give the Repository layer.
2. The Framework. This project is at the same time a tool and a Lua
config framework, both are highly coupled, but for simplicity and clear
separation of concerns I keep the framework logic, that is at the end
basically a small subproject, granting Lua the tools to be useful
(since for security I removed all its stdlib operations, so this is
basically a stdlib replacement in pure Rust).

#### The WebFramework Analogy

I already entered in detail on a few decisions I take, but to simplify
the explanation of the more general ones I want to do an analogy with
a Web Framework and the responsibilities I want to add to the layers.
The CLI args are the HTTP request. Actions are the endpoint handlers,
each one orchestrates services and returns results. Services hit the
repositories and the evaluator for data. Presentation renders the
response, every string the user sees with color that stays off on
pipes. Main connects both sides and knows nothing about either one,
exactly like a framework passing a request to a handler and a response
to a renderer.

Security utilities stay a pseudo-layer for now. The shared hash
function lives there because digests belong to no domain. I dont know
yet if it grows into a project-wide Utility layer like model, or stays
security-specialized with validation and secrets encoding in the plan
later. That decision waits.

Behavior stays identical throughout. Tests follow the moves and the
Lua surface stays untouched.
